# Game Terrarium 強化学習化・段階成長プラン

> 提案対象: `game_terrarium` に登録されている全11体験 + 新規2案  
> 基準実装: `apps/arena-shooter/`  
> 作成日: 2026-07-23  
> ステータス: 提案

## 1. 提案の要約

各プロジェクトを、複雑なルールを眺める独立した実験から、次の共通体験を持つ
「学習する小さなゲーム」へ再設計する。

> **最初は数秒から数十秒で失敗し、失敗のたびに学習する。  
> 学習が進むほど生存時間・到達距離・処理量が伸び、GAME OVER の間隔も長くなる。**

`Arena Shooter` は、この方向の基準として使える。すでに以下を備えているためである。

- 状態を離散化した軽量な Q-learning
- 行動、即時報酬、エピソード終了報酬
- 撃墜後の自動再出撃
- 学習モデルと恒久進行の保存
- Wave、生存時間、報酬、探索率、学習ステップの可視化
- headless シミュレーション

ただし、Arena Shooter の大きな戦闘・武器・恒久成長を全作へコピーするのではない。
移植するのは、**短いエピソード、明確な失敗、少数の行動、成長の可視化**という骨格である。

## 2. この企画で実現したい体験

### 2.1 目標とする学習カーブ

| 段階 | 典型的な1エピソード | GAME OVER | 学習の見え方 | 観察者の印象 |
|---|---:|---|---|---|
| 初期 | 5〜30秒 | 頻繁 | 数回ごとに行動が変わる | 「まだ下手だが、試している」 |
| 習熟 | 30秒〜3分 | 減少 | 危険への対応が目に見えて改善 | 「前より明らかに上手い」 |
| 熟練 | 3〜10分 | まれ | 記録更新は緩やか | 「長く安定して任せられる」 |
| 停滞突破 | 課題依存 | 意図的に再増加 | 新しい敵・地形へ再適応 | 「新しい壁に挑戦している」 |

横軸を総プレイ時間、縦軸を代表的な生存時間とすると、理想は一直線ではなく、
失敗と停滞を含む階段状になる。

```text
生存時間
  ^
  |                              ┌──── 熟練
  |                    ┌─────────┘
  |          ┌─────────┘  新課題で一時低下
  |    ┌─────┘
  | ┌──┘
  +------------------------------------> 総プレイ時間
    失敗多数     習熟          更新はゆっくり
```

後半に GAME OVER が減るため、エピソード終了時だけ学習すると更新頻度が極端に落ちる。
そのため、学習は次の二つを併用する。

1. **オンライン更新**: 画面上の行動ごとに小さく更新する
2. **エピソード更新**: GAME OVER 時に大きな結果を確定する

これにより、「後半ほど学習がゆっくり」という体感を維持しつつ、長いエピソード中も
完全には学習が止まらない。

### 2.2 人間の役割

人間は常時操作するプレイヤーではなく、学習環境の管理者になる。

- 学習を眺める
- Champion と前世代の差を見る
- 報酬方針を少数のプリセットから選ぶ
- 新しい難度や課題を解放する
- 必要なときだけ行動を上書きする

人間の介入を必須にはしない。無操作でも失敗、学習、再挑戦が続くことを全作の条件とする。

## 3. 共通設計

### 3.1 1ゲームを構成する最小要素

各ゲームは最初に以下だけへ絞る。

| 要素 | 上限の目安 | 目的 |
|---|---:|---|
| 観測値 | 6〜12個 | 何が危険かを学べる最小情報 |
| 離散行動 | 4〜10個 | 行動結果を人が理解できる範囲 |
| 即時報酬 | 3〜5種類 | 生存だけでなく上達の方向を示す |
| 終了条件 | 1〜2種類 | 失敗の意味を明確にする |
| 難度変数 | 1つ | 学習進行と難度を調整しやすくする |
| 代表指標 | 1つ | 前より伸びたことを一目で示す |

複雑な資源経済、複数AI人格、大量の強化、LLMによる細かな判断は、最初の学習版から外す。
学習が成立した後に、観察価値が高いものだけを戻す。

### 3.2 共通エピソードループ

```text
初期化
  ↓
観測 → 行動選択 → ゲーム更新 → 即時報酬
  ↑                              ↓
  └──────── 生存中 ─────────────┘
                                 ↓
                            GAME OVER
                                 ↓
              結果確定 → モデル保存 → 1〜2秒で再開
```

全作で `GAME OVER` は停止画面ではなく、短い学習結果表示にする。

表示例:

```text
EPISODE 42
SURVIVED 01:18   +12 sec vs previous
BEST 02:06
REWARD +184
LEARNED: avoided overload earlier
REDEPLOYING IN 1.5s
```

### 3.3 学習と恒久強化を混同しない

「長く生きた理由」が AI の改善なのか数値強化なのか分からないと、学習を眺める面白さが失われる。

- **Skill**: 方策・Q値の更新。判断が上手くなる
- **Power**: HP、火力、処理能力などの恒久強化
- **Difficulty**: 敵量、速度、故障率などの環境強化

画面とセーブで三者を分離する。基本の評価は同じ Power と同じ seed で旧モデルと新モデルを
比較し、Skill の差だけを表示する。

初期フェーズでは Power 強化を入れず、Skill だけで伸びるかを先に検証する。

### 3.4 Champion / Training の二系統

- **Training**: 探索を含む現在の学習モデル
- **Champion**: 固定 seed 評価で最良だった安定モデル

一定数のエピソードごとに両者を同条件で評価し、Training が上回ったときだけ Champion を更新する。
観察画面は通常 Training を表示するが、ワンクリックで Champion や前世代リプレイへ切り替えられる。

後半のエピソード長期化への対策として、CPU負荷の上限内で、描画なし・倍速の短い
Training エピソードをバックグラウンドに1本だけ走らせる。常時大量並列にはしない。
長時間常駐というリポジトリの目的に合わせ、フレーム時間またはCPU使用率が閾値を超えたら停止する。

### 3.5 難度は学習に追従させる

単純な無限難化では、学習前に失敗し続けるか、学習後に簡単すぎる状態になる。
難度は Champion の成績に基づく段階制にする。

- 直近評価の成功率が `70%` を超えたら次の Tier を試す
- `30%` 未満なら現在 Tier で訓練を続ける
- 新 Tier の最初は失敗が増えてよい
- 過去 Tier の評価を混ぜ、以前の技能を忘れていないか確認する
- 1エピソードに安全上限を設け、無限に終わらない場合は「時間切れ成功」として区切る

この仕組みが、階段状の成長と定期的な新しい見どころを作る。

## 4. プロジェクト別の再設計案

### 4.1 優先度一覧

| 優先 | プロジェクト | 簡略化後の学習課題 | 代表指標 | 判断 |
|---:|---|---|---|---|
| 基準 | Arena Shooter | 移動・回避・射撃 | 生存時間 / Wave | 共通仕様の抽出元 |
| 1 | Network Defense | 防壁・増援・修復の選択 | 防衛時間 / Wave | 最も移行しやすい |
| 2 | One-Line RPG（新規） | 間合い・防御・連撃・必殺技 | 到達距離 / 連勝数 | 1ライン格闘RLとして作りやすい |
| 3 | Drone Bastion TD（新規） | 操作機切替・重機動・壁防衛 | 防衛時間 / Wave | 既存Escort TDを加工して作る |
| 4 | Escort TD | 護衛隊形と進退 | 護送距離 | 終了条件と headless が既存 |
| 5 | City Traffic | 信号フェーズ切替 | 無事故時間 / 流量 | 小さな制御問題にしやすい |
| 6 | Network Ecosystem | 免疫投入位置の選択 | 生態系安定時間 | 観察性が高い |
| 7 | Colony | 1勢力の資源配分 | コロニー生存時間 | 多勢力AIを先に削る |
| 8 | Planet Strategy | 1帝国の物流判断 | 勝率 / 生存時間 | 状態が大きく、第二段階向き |
| 9 | MOSS | パケットの次ホップ選択 | 無輻輳時間 / 配送率 | server runtimeとの分離が必要 |
| 10 | Submarine Cables | 障害時の経路切替 | 通信維持時間 | ルーティング課題として統合可 |
| 11 | Submarine Network 3D | 同上 | 同上 | 3D表示モードへ統合推奨 |
| 12 | Network Small World | 辺の追加・切断 | 配送効率維持時間 | Ecosystem/MOSSとの重複を整理 |

#### Arena Shooter — 基準実装

残すもの:

- 離散観測・離散行動の Q-learning
- 自動再出撃、モデル保存、headless シミュレーション
- Wave と学習情報のHUD

先に簡略化するもの:

- 初期検証では機体を1種、主武器を1種、強化選択を3種程度に限定
- Skill評価中は恒久火力と Ascension を固定
- 観測・行動・報酬の定義をゲーム本体から分離

追加するもの:

- Champion 評価
- 生存時間の移動中央値
- 「世代ごとの改善理由」の短い表示
- エピソード時間分布を検証する自動試験

目標カーブ: 初回中央値 `15〜30秒`、30エピソード後 `60〜120秒`。

#### Network Defense — 最初の移植候補

現在ある Wave、SERVER DOWN、スコア、履歴、headless 実行を利用できる。
複数ランクの個別ルールとLLM更新を一度外し、AIの行動を次へ絞る。

- 最危険ノードへ Junior を送る
- Firewall を張る
- 感染ノードを reboot する
- server を harden する
- credits を温存する

観測は server HP、敵数、感染数、firewall数、credits、Wave、最大危険方向。
報酬は生存、撃破、感染除去、未使用creditsへ小さな正、server被害と陥落へ負。
初期資源を厳しくして `20〜40秒` で陥落させ、学習後に Wave が伸びる形にする。

#### One-Line RPG（新規）— 無限ベルトコンベア格闘RPG

横一列のリアルタイム戦闘とRPG成長を組み合わせる。発想の基準は
『テイルズ オブ ファンタジア』のような、1本の戦闘ライン上で間合いを詰め、
通常攻撃、術技、防御をリアルタイムに出す戦闘である。ただしステージクリア型にはせず、
背景と地面が左へ流れ続ける無限ベルトコンベアにする。

参考: バンダイナムコ公式の
[GBA版『テイルズ オブ ファンタジア』紹介](https://www.bandainamcoent.co.jp/cs/list/talesofphantasia_gba/intro.html)
では、同作の戦闘をアクション要素を取り入れた「リニアモーションバトルシステム」と説明している。

```text
進行方向 →

 [過去の地形]  HERO ⇄ ENEMY  [次の敵・イベント]  BOSS ...
  ←────── 世界全体は左へスクロールし続ける ──────

       hitbox ┌────┐       ┌──┐ hurtbox
        HERO  │剣撃│──────>│敵│
              └────┘       └──┘
```

探索中も戦闘中もスクロールは止めない。敵が画面右から入り、AIは左へ押し流される前に
接近、回避、ガード、攻撃を組み立てて倒す。敵を倒すと次の敵または短いイベントが流入し、
戦闘が途切れず続く。画面左端へ押し出されるかHPが0になると GAME OVER。

##### 操作と行動空間

AIへ、人間が格闘ゲームを遊ぶときに近い仮想パッドを渡す。

- `LEFT` — 後退、間合いを外す
- `RIGHT` — 前進、ダッシュ開始
- `UP` — ジャンプ、上段回避、空中技への始動
- `DOWN` — しゃがみ、低姿勢回避、下段技への始動
- `GUARD` — 防御。方向と組み合わせて立ち／しゃがみガード
- `LIGHT` — 発生が速く隙が小さい弱攻撃
- `HEAVY` — 発生が遅く隙が大きい強攻撃
- `HEAL` — 回数またはゲージを消費する回復
- `SPECIAL` — 必殺技。必殺ゲージを消費

初期の tabular Q-learning では同時押しを自由結合させず、`RIGHT+LIGHT`、
`DOWN+GUARD`、`UP+HEAVY`など、有効な組み合わせを12〜18個の離散アクションとして定義する。
入力履歴による長いコマンド技は第2段階とし、最初は方向と攻撃ボタンの組み合わせで必殺技を出す。

操作自体は段階解放せず、第1エピソードから上下左右、防御、弱攻撃、強攻撃、回復、
必殺技をすべて選択可能にする。学習を簡単にするために減らすのは操作ではなく、
最初に登場する敵の種類と同時出現数である。

##### 3つの職業

最初の職業は戦士、魔法使い、格闘家の3種とする。全職業が同じ仮想パッドを使うが、
ボタンから発生する技、射程、消費リソース、飛び道具の有無が異なる。

| 職業 | 戦闘距離 | 弱攻撃 | 強攻撃 | 飛び道具 / 必殺技 | 防御特性 |
|---|---|---|---|---|---|
| 戦士 | 近〜中距離 | 速い剣撃 | 踏み込む大振り | 短い剣圧。必殺は広範囲斬撃 | ガードが強く、移動は遅め |
| 魔法使い | 中〜遠距離 | 短射程の魔力弾 | 詠唱付きの貫通弾 | 通常技から飛び道具を使える。必殺は大魔法 | ガードが弱く、後退と距離維持が重要 |
| 格闘家 | 密着〜近距離 | 最速の拳連打 | 打ち上げ・突進打撃 | 通常は近接。気弾はゲージ消費技 | 回避と反撃が強く、射程が短い |

3職業を1つのQ-tableへ混ぜない。観測形式と行動IDは共有しつつ、
`warrior / mage / fighter`ごとに独立した方策を保存する。同じ状況でも、
戦士はガードして踏み込み、魔法使いは後退して射撃し、格闘家は回避から接近するという
職業差を学習結果として見せる。

クールダウン中、ゲージ不足、空中専用など、その瞬間に実行不能な行動は
`action mask`で候補から外す。AIが使用不能技を何度も選んで学習を浪費することを防ぐ。
一方、単に不利な行動はマスクせず、報酬から不利だと学ばせる。

職業はエピソード開始時に `AUTO / WARRIOR / MAGE / FIGHTER`から選択できる。
`AUTO`は各職業の出撃回数が偏らないよう循環させる。固定seed評価は職業別に行い、
Championも職業ごとに保持する。

##### 最初から全操作を学習させるQ学習方式

全操作を最初から扱うことは可能だが、ピクセル座標と全入力履歴をそのまま状態にすると
Q-tableが巨大になる。次の制約で表形式Q-learningの範囲へ収める。

- 行動は任意の同時押しではなく、意味のある12〜18個のコマンドへ整理する
- 距離、HP、ゲージ、発生時間を3〜5段階へ離散化する
- 敵が複数いても、最寄り・攻撃中・背後の脅威へ要約する
- 職業別にQ-tableを分ける
- 新規状態には職業別の小さな事前値を与える
- 最初から全操作を使えるまま、敵だけを単発攻撃1体から複雑化する

事前値は正解を固定するものではなく、完全ランダム期を短くする初期バイアスとする。
例えば戦士は近距離ガード、魔法使いは遠距離射撃、格闘家は近距離弱攻撃を少し高く始める。
その後は通常の探索と報酬で上書きされる。

状態数が上限を超える場合は操作を削らず、まず観測の区切り方を見直す。それでも不足する場合だけ、
表形式Q-learningから線形近似Qまたは小型DQNへ移行する。ユーザーに見える操作体系は変えない。

##### 当たり判定ベースの戦闘

攻撃結果は確率計算だけにせず、毎フレームの当たり判定で決める。

- `hurtbox` — キャラクターが被弾する領域
- `hitbox` — 攻撃中の有効領域
- `pushbox` — キャラクター同士が重ならないための領域
- `guardbox` — ガード方向と成立時間
- `projectile` — 飛び道具の位置、速度、寿命

各技は `startup / active / recovery` の3区間を持つ。弱攻撃は発生が速いが短射程、
強攻撃は長射程・高威力だが空振り時の隙が大きい。防御成功時は被害を軽減するが、
ガードゲージを消費する。これによりAIが「近いから弱攻撃」「敵の大技後に強攻撃」
「攻撃予兆を見て防御」という格闘ゲーム的な対応を学べる。

当たり判定、ノックバック、無敵時間、ヒットストップは決定論的に処理する。
同じseedと入力列なら同じ結果になることを、Champion比較の前提にする。

##### アルゴリズムで動く敵

敵は学習モデルではなく、読みやすい有限状態機械で動かす。

```text
APPROACH → ATTACK_WINDUP → ACTIVE → RECOVERY
    ↑           ↓                    ↓
 RETREAT ← GUARD / EVADE ←──── COOLDOWN
```

敵ごとに射程、予兆時間、上下段、連撃数、後隙を変える。

- `Slime` — 接近して遅い単発攻撃。防御学習用
- `Wolf` — 素早い突進と後退。間合い管理用
- `Guard` — 正面防御と反撃。強引な連打を抑える
- `Archer` — 遠距離攻撃。接近とジャンプ回避用
- `Boss` — 複数パターンとフェーズ変化。総合試験

アルゴリズム敵にすることで、攻撃予兆と当たり判定の関係を固定できる。
Tier上昇時は単純なHP増加より、敵の組み合わせ、攻撃パターン、上下段、飛び道具を追加する。

##### 観測

- 自分と敵のHP帯
- 自分と最寄り敵の距離帯、左右関係、高さ
- 自分と敵の現在モーション
- 敵攻撃の予兆、攻撃種別、残り発生時間帯
- 自分のガード、回復、必殺ゲージ
- 画面左端までの危険距離
- 同時に存在する敵数と飛び道具の危険方向
- 直前行動とコンボ段数

座標をピクセル値のまま渡さず、`接触 / 近い / 中距離 / 遠い`のように離散化する。
敵が複数いる場合も全員分を並べず、最寄り、攻撃予兆中、背後の脅威へ要約する。

##### 報酬

- 有効打、コンボ継続、敵撃破、右方向の新記録へ正
- ジャストガード、攻撃回避、必殺技で複数敵を巻き込むと追加の正
- 被弾、ガード破壊、空振り、回復の無駄遣いへ負
- 左端へ追い込まれている時間と、敵がいない場面での停滞へ小さな負
- HP 0または画面外へ押し出されると大きな負
- Boss撃破とイベント突破へ大きな正

ダメージ量だけを強く報酬すると連打へ偏るため、防御成功、被弾回避、後隙への反撃も
別報酬にする。一方で防御し続ける抜け道を防ぐため、スクロール圧と撃破期限を持たせる。

##### 無限進行とイベント

基本単位は `通常敵2〜5戦 → イベント → Elite → 通常戦 → Boss` とする。
イベントは戦闘を止めず、ベルト上へオブジェクトとして流す。

- 回復泉 — 接触すると少量回復するが、敵への対応が遅れる
- 宝箱 — 攻撃して開ける。武器または一時強化
- 落石 — 上下入力や防御で回避
- 商人 — 数秒だけ選択肢を出し、無操作ならAIが選ぶ
- 分岐札 — 安全、報酬、Eliteの次セクションを選ぶ
- 救援対象 — 一定時間守ると報酬

イベントの出現順はseed管理し、イベント選択も戦闘方策とは別の小さな価値表で学習させる。

##### 学習カーブ

初期モデルは弱攻撃を空振りし、防御と回復のタイミングを誤って `15〜30秒` で倒れる。
学習が進むと、次の順で目視できる改善を期待する。

1. 敵が近づいてから攻撃する
2. 攻撃予兆へガードまたは回避を合わせる
3. 弱攻撃から強攻撃へ連携する
4. 後隙へ必殺技を使う
5. 複数敵とイベントを含む状況でゲージを温存する

代表指標は到達距離、連勝数、被弾せず倒した敵数、Boss撃破数。
HP 0または押し出しで終了し、1〜2秒後に自動再出発する。

恒久成長は技、必殺技、回復方法、装備スロットの解放を中心にする。
最大HPや攻撃力を上げる場合も、Skill固定評価では装備と数値を固定する。

One-Line RPGは状態数がArenaより増えるが、操作は最初からすべて使用可能にする。
最初は予兆の長い敵1体だけを出し、学習が進んだら高速攻撃、上下段、飛び道具、
複数敵、イベントを順に追加する。カリキュラムで変えるのは敵環境であり、AIの操作ではない。

#### Drone Bastion TD（新規）— チェスドローン中央塔防衛

> MVP実装済み: `apps/drone-bastion/`

既存の `Escort TD` を加工し、移動するKINGを守るゲームから、画面中央の巨大な
`KING TOWER`を守る全方向タワーディフェンスへ作り直す。チェスモチーフ、敵の経路探索、
Wave、投射物、壁に利用できるグリッドなどは流用し、護送ルートと随伴隊形は外す。

大量の敵が外周から塔へ押し寄せ、壁で時間を稼ぎながら少数の重いドローンで迎撃する。
方向性は「少数の操作ユニットを持つThey Are Billions型の拠点防衛」とする。

```text
       ENEMY WAVE ↓↓↓
   ┌──── WALL / GATE ────┐
   │ Rook       Pawn      │
   │       [KING TOWER]    │
   │ Bishop       Knight   │
   └──── WALL / GATE ────┘
       ↑↑ ENEMY WAVE ↑↑

   RL CONTROL: Rook 1/4
   他の3機: 停止位置から自動砲撃
```

##### 一度に直接操作できるのは1機

複数のドローンを所有できるが、RLが移動・旋回・射撃を直接操作するのは常に1機だけ。
行動に `SELECT_NEXT`、`SELECT_PREVIOUS`、または脅威方向にいる機体を選ぶ
`SELECT_SECTOR`を含め、戦況に合わせて操作チャンネルを切り替える。

操作対象から外れたドローンは、即座に静止するのではない。機体の自動制動が働き、
慣性に従って減速・停止した後、その位置へアンカーを下ろして自動砲台になる。
自動砲台時は射程内の敵をアルゴリズムで狙うが、移動、壁修理、能力使用は行わない。
再選択するとアンカー解除の短い遅延後に操作可能になる。

これによりRLは、単に強い1機を動かし続けるのではなく、
「Rookを北壁へ置いて砲台化 → Knightへ切り替えて突破敵を迎撃 → Bishopを選んで南を援護」
という配置と切替を学ぶ。

##### 最大ドローン数

初期保有数は2機、戦場へ同時展開できる最大数は**6機**とする。

- 直接操作チャンネル: 1
- 自動砲台チャンネル: 最大5
- 同一画面のドローン物理・射撃・観測対象: 最大6

6機ならチェス駒の種類を見せつつ、切替候補、Q状態、投射物、描画負荷を抑えられる。
7機目以降は増やさず、余剰機体を修理用reserveまたは恒久資源へ変換する。
負荷計測で余裕があっても、観察上の役割が読みにくくなるため通常上限は増やさない。

##### チェス駒ドローンと重い移動

すべての機体は速度を直接変更せず、推力、質量、摩擦、制動力から移動する。
入力を離してもすぐには止まらず、重い機体ほど加速、旋回、ブレーキに時間がかかる。
壁や敵へ質量を持って衝突し、軽量機と重量機で押し合いの結果も変える。

| 駒 | 車体・移動感 | 主武装 | 自動砲台時の役割 |
|---|---|---|---|
| Pawn | 軽量装輪車。加速と制動が速い | 短射程連射 | 壁の穴と小型敵を処理 |
| Knight | 中量ホバー。旋回しながら横滑り | 突進砲 / 散弾 | 近距離の突破敵を止める |
| Bishop | 中量長射程車。斜め方向の移動が得意 | 貫通レール砲 | 長い射線で複数敵を抜く |
| Rook | 重戦車。キャタピラ式の信地旋回 | 重砲 / ノックバック弾 | 壁の後ろから正面を固定防衛 |
| Queen | 終盤用の高コスト万能機 | 複合武装 | 射程と方向を問わない穴埋め |

特にRookは戦車らしく、左右キャタピラの差動で前後移動と信地旋回を行う。
横移動はできず、最高速へ達するまで時間がかかり、逆噴射しても制動距離が長い。
他の駒も同じ物理法則を使いながら、質量、推力方向、旋回慣性、制動力で個性を出す。

##### 壁と敵の進軍

KING TOWERの周囲へ、セル単位の壁とゲートを設置できる。敵は塔までの経路を探索し、
開いている経路を優先する。完全に閉じられた場合は、最も弱い壁へ集まって破壊する。

- 壁 — 安価。敵の足を止め、射撃時間を作る
- 強化壁 — 高耐久だが修理費が高い
- ゲート — ドローンは通過できるが、敵に狙われやすい
- 地雷セル — 使い切り。大量敵の圧を一時的に減らす

初期マップは塔を囲う二重の四角い壁と東西南北4ゲートに固定する。
RLへ自由な壁建築を最初から任せず、操作機が近くの壁を`REPAIR`または
`REINFORCE`するところから始める。学習成立後に、破壊済みセルへの再建と、
限られた候補セルへの新設を加える。

敵は少数の高HP敵だけでなく、壁へ密集する大量の小型敵を主役にする。
敵数にはsoft capを設け、上限付近では個体追加ではなく群れ単位のHP・圧力表現へまとめる。

##### RLの行動

- 前進 / 後退
- 左旋回 / 右旋回
- 制動
- 主武装を射撃
- 機体固有能力を使用
- 次 / 前 / 危険セクターのドローンへ操作切替
- 近くの壁を修理 / 強化
- 待機して自動照準へ一時移行

全行動は第1エピソードから利用可能にする。ただし機体ごとに不可能な移動や、
弾薬・クールダウン不足の能力はaction maskで除外する。

##### 観測

- KING TOWERのHP帯
- 東西南北4セクターの敵密度、最短距離、壁HP
- 現在操作中の駒、位置、向き、速度帯、停止距離帯
- 全ドローンの生存状態と配置セクター
- 各ドローンが操作中 / 制動中 / 自動砲台中のどれか
- 弾薬、機体固有能力、修理資源
- 壁の破口と塔へ到達可能な最短経路

非選択5機の細かな座標をすべて状態へ入れず、配置セクター、役割、危険度へ要約する。
操作機だけは速度と向きを詳しく観測し、重い慣性を学べるようにする。

##### 報酬

- 敵撃破、壁の外側での迎撃、Wave突破へ正
- 自動砲台が有効射撃を続ける配置へ小さな継続報酬
- 破口の修理、塔へ近い敵へのノックバックへ正
- KING TOWER被弾、壁破壊、ドローン損失へ負
- 衝突、空撃ち、切替直後の無意味な再切替へ小さな負
- KING TOWER破壊へ大きな負

操作していない砲台の撃破報酬も、現在のRL方策へ帰属させる。どこへ置いて切り替えたかが
方策の成果だからである。ただし過去の配置効果を学びやすくするため、切替時の状態と
その後数秒の砲台報酬を結ぶn-step更新を使う。

##### 「機数を増やす」か「性能を上げる」か

Wave間に、同じ資源を使う二択を出す。

1. **DEPLOY** — 上限6機まで新しいドローンを1機追加する
2. **UPGRADE** — 既存1機の武装、装甲、推力、制動、砲台性能を上げる

機数を増やすと守れる方向と自動砲台の数が増えるが、切替判断と修理対象も増える。
性能を上げると1方向は強くなるが、反対側の破口へ対応しにくい。
上限到達後はDEPLOYを候補から外し、機体の役割分化または壁強化を提示する。

この選択も戦闘行動とは別のQ値で学習し、Wave帯、現在の機数、壁の損傷、
所有する駒の偏りを状態にする。

##### 学習カーブ

初期モデルは重いRookで塔の周りを行き来しようとして間に合わず、他機も悪い場所へ置くため、
`20〜40秒`で最初の壁を破られてGAME OVERになる。学習が進むと次の改善が見える。

1. ブレーキ開始を早め、壁や塔へ衝突しなくなる
2. 非操作機を射線の通る位置で自動砲台化する
3. 危険セクターに近い機体へ切り替える
4. Rookを正面固定、Knightを破口対応のように役割分担する
5. 敵構成に応じて機数追加と単機強化を選び分ける
6. 壁を使って大量敵を狭い射線へ集める

成長は `Skill / Fleet / Wall / Threat Tier` の4層に分ける。
Skill固定評価では機体構成、強化値、壁配置、敵seedを固定し、切替と操縦だけを比較する。

##### MVP実装範囲

2026-07-23時点のMVPでは、軽量Canvas描画と決定論的なheadlessコアを採用し、以下を実装した。

- 中央KING TOWERと16枚の初期壁
- 外周4方向から塔へ進むswarm / bruteのWave
- PawnとRookの2機から開始
- 推力、旋回、慣性、制動、最高速度の機体別物理
- 直接操作1機、切替後の自動制動、自動砲台化
- 最大6機
- 共通`TabularQAgent`による移動、射撃、制動、操作機切替
- Wave突破時のDEPLOY / UPGRADE学習
- GAME OVER後のモデル保存と自動再出撃
- 固定seed再現、重機動差、砲台化、6機上限の自動テスト

MVPでは自由な壁建築、Knight / Bishop / Queen、壁修理行動、Champion評価は未実装。
まずPawn / Rookだけで、操作機切替と重い慣性をQ学習できるかを検証してから追加する。

#### Escort TD — 「配置ゲーム」から「護衛判断」へ

都市生成、駒の種類、複雑な配置を最初から学習対象にしない。
KINGを中心とした3レーンだけに簡略化する。

行動:

- 前衛を前・左・右へ寄せる
- 後衛を集中・分散する
- 進む / 停止する
- 予備兵を投入する

観測は KING HP、前左右後の脅威、護衛残数、予備資源、進行率。
KING撃破が GAME OVER、都市到達が成功終了。代表指標は護送距離。
既存の CHIP 恒久成長は Skill 検証後に戻す。

#### City Traffic — 信号制御サバイバル

車両個別制御ではなく、1交差点または2交差点の信号制御だけを学ばせる。

行動は南北青、東西青、右折フェーズ、現状維持。観測は各方向の待ち台数、
最長待ち時間、交差点内車両、直前フェーズ。衝突または渋滞上限で GAME OVER。
報酬は通過台数と安全継続へ正、待ち時間と急な切替へ小さな負、衝突へ大きな負。

初期は交通量を高くしてすぐ詰まらせる。学習後は交通量 Tier を上げる。
見た目には青信号の意図、危険方向、予測した次行動を路面色で示す。

#### Network Ecosystem — 免疫オペレーター

現在の threat / immune / carnivore / resource の生態系を残し、人間が行っている
ノードへの介入をAI行動へする。学習対象は「どのノードへ、どの介入をするか」だけ。

初期版は介入を `immuneを置く / 置かない` に絞る。server resource が0、
または脅威ノード比率が一定以上で GAME OVER。報酬は資源総量、脅威抑制、
介入コストの少なさで構成する。代表指標は安定維持時間。

#### Colony — 1コロニーの資源配分

最初は3勢力の性格比較と領土戦争を外し、1勢力対環境にする。

行動は食料採取、資材採取、人口増加、防衛、拠点拡張。観測は食料、資材、人口、
脅威、空き領域、直近の収支。食料枯渇または拠点破壊で GAME OVER。
生存時間と最大人口を代表指標にする。

学習成立後、同じ観測・行動を持つ Champion を3体対戦させる。
人格は別ロジックではなく報酬ウェイトの差として戻す。

#### Planet Strategy — 物流サバイバル

現行の4種AI、艦隊戦、複数目的を同時に学ばせない。最初は1帝国の物流だけにする。

行動は採掘増強、輸送船生産、工場維持、航路変更、防衛投資。
観測は総資源、稼働工場、輸送船数、配送遅延、敵脅威、残り惑星。
工場停止の継続または輸送船全滅で GAME OVER。代表指標は帝国生存時間。

第2段階で固定ルールの敵を1勢力追加し、第3段階で Champion 同士のリーグ戦にする。
現行8分判定は評価試合の上限として再利用する。

#### MOSS — パケットルーティング

表示と server-side runtime を維持し、学習問題を次ホップ選択へ限定する。

観測は隣接辺ごとの待ち行列、遅延、故障、目的地までの距離。行動は隣接辺の選択。
配送成功へ正、遅延とループへ負、キュー溢れで GAME OVER。代表指標は無輻輳時間と配送率。
全パケットに別々のモデルを持たせず、共有方策を使う。

#### Submarine Cables / Submarine Network 3D — 1ゲーム・2表示

この2作は学習課題を共通化し、2Dと3Dの表示モードとして統合する。

行動は故障区間の迂回、帯域配分、修理優先順位。観測は障害位置、各経路の負荷、
未配送量、修理残時間。重要拠点の接続断または未配送量上限で GAME OVER。
代表指標は通信維持時間。

シミュレーションコア、RL、セーブ、評価を共通にし、2D/3Dレンダラーだけを分ける。

#### Network Small World — トポロジー保守

純粋なネットワーク可視化から、制限予算内で接続を保つゲームへ変える。

一定間隔で辺が故障し、AIは1本追加、1本修理、低価値な辺を切る、待機から選ぶ。
server孤立または平均配送遅延上限で GAME OVER。代表指標は接続維持時間。

ただし MOSS と役割が近い。先に MOSS のルーティングを完成させ、異なる面白さが
出なければ独立ゲームにせず、MOSSの「Topology Engineer モード」へ統合する。

## 5. 共通実装アーキテクチャ案

ゲームごとに Q-learning を複製せず、共有ランタイムを作る。

```text
shared/rl/
  rl_types.ts          Observation / Action / Transition / EpisodeResult
  tabular_q_agent.ts   ArenaのQ-learningを汎用化
  trainer.ts           step更新、episode終了、探索率
  evaluator.ts         Champion比較、固定seed評価
  curriculum.ts        Tier昇降
  model_store.ts       version付きserialize/restore
  metrics.ts           中央値、成功率、学習速度

各ゲーム:
  *_environment.ts     reset / observe / step / isDone
  *_reward.ts          報酬定義
  *_render.ts          描画のみ
  *_rl_ui.ts           共通HUDへの表示変換
```

### 5.1 共通化の実装状況

2026-07-23時点で、第一段階として以下を実装済み。

- `shared/rl/rl_types.ts`
  - 汎用の行動決定、Q-table保存、エージェント設定型
- `shared/rl/tabular_q_agent.ts`
  - 状態キー化、action mask、ε-greedy選択、TD更新、終端更新、保存復元
- `apps/arena-shooter/arena_shooter_agent.ts`
  - 共通エージェントを使うArenaアダプターへ移行
  - 機体別action mask、Arena固有の初期Q値、0.09秒の判断間隔を維持
  - 既存`version: 1`セーブとアップグレード価値を維持
- `scripts/tabular_q_agent.test.ts`
  - 行動選択、action mask、遷移学習、終端学習、保存復元、探索率上限を検証

共通化したのは学習アルゴリズムだけであり、観測、報酬、行動内容、判断間隔、
初期Q値は各ゲーム側に残している。次のゲームは、これらを設定として渡すことで
同じ学習・保存・検証機構を利用できる。

第二段階として、Network Defenseへの最初の横展開も実装済み。

  - server HP、感染、敵、firewall、credits、Waveを離散観測へ変換

- RLモデルをlocalStorageへ保存し、勝敗後約1.8秒で自動再挑戦
- HUDへ現在行動、探索か方策か、探索率、既知状態数を表示

- `scripts/network_defense_rl.test.ts`で観測、行動、保存復元、終端更新を検証

#### Network Defense 学習効果の固定seed評価

`scripts/network_defense_rl_learning_eval.ts`で、未学習モデルと学習後モデルを
同じ20seed、探索率0、学習更新停止の条件で比較できる。headless内の`Math.random()`と
ゲーム時間もseedへ固定し、同じ実行は同じ結果になる。

300エピソード学習後の実測:

| 指標 | 未学習 | 300エピソード後 | 差 |
|---|---:|---:|---:|
| 勝利数 / 20 | 8 | 12 | +4 |
| 敗北数 / 20 | 7 | 6 | -1 |
| 平均到達Wave | 8.95 | 9.75 | +0.80 |
| 平均生存時間 | 237.9秒 | 256.7秒 | +18.8秒 |
| 平均スコア | 1793.95 | 2228.9 | +434.95 |
| 平均Server残HP | 6.25 | 8.55 | +2.30 |

80エピソード時点では生存時間の改善が見られず、300エピソードで初めて明確な差が出た。
現状は「学習効果はあるが、立ち上がりが遅い」と評価する。次の改善対象は、
50〜100エピソードでも生存改善が見える報酬と状態表現、およびChampionモデル保護である。

再実行:

```bash
npm run eval:network-defense-rl
```

最小インターフェース:

```ts
interface RlEnvironment<Observation, Action> {
  reset(seed: number, tier: number): Observation;
  observe(): Observation;
  step(action: Action, dt: number): {
    observation: Observation;
    reward: number;
    done: boolean;
    reason?: string;
  };
}
```

最初は Arena と同じ表形式 Q-learning を採用する。依存追加がなく、保存が簡単で、
Q値や探索行動を画面に説明しやすい。状態数が増える Planet Strategy などで限界を確認してから、
DQN等の導入を別判断にする。最初から全作へニューラルネットを導入しない。

## 6. UI共通仕様

全作に同じ位置・用語の「Learning HUD」を付ける。

必須表示:

- `GEN` — Champion更新回数
- `EP` — エピソード数
- `AGE` — 現エピソードの生存時間
- `BEST` — 最高記録
- `MEDIAN 10` — 直近10回の中央値
- `TIER` — 現在難度
- `EPSILON` — 探索率
- `ACTION` — 現在行動
- `REWARD` — 直近と累積
- `WHY` — 行動理由を観測値から短く説明

グラフは細かい損失値より、直近30エピソードの生存時間を主役にする。
改善・停滞・新Tierでの一時悪化が一目で分かるためである。

行動の視覚化:

- 選択対象を発光
- 危険として認識した方向を赤
- 移動・配送・防衛の意図を矢印
- 探索行動には `EXPLORE` バッジ
- Champion更新時だけ短い演出

## 7. 導入ロードマップ

### Phase 0 — カーブの基準化（1〜2週間）

Arena Shooter を共通仕様の基準にする。

- 100〜300エピソードの headless 計測
- 初回、10回、30回、100回時点の生存時間中央値を保存
- Champion / Training 評価の追加
- Skill と Power を固定した比較モード
- 共通型と保存形式の設計

完了条件: 同じ seed と装備で、世代更新による成績向上を再現できる。

### Phase 1 — 共通RLランタイム（1〜2週間）

- Arena の agent を `shared/rl/` へ抽出
- 共通 Learning HUD
- model version、壊れたsaveのfallback、リセット機能
- headless 評価ハーネス

完了条件: Arena と最小サンプル環境が同じ trainer で動く。

### Phase 2 — 近い既存2作へ移植（2〜4週間）

1. Network Defense
2. Escort TD

既存の終了条件と headless シミュレーションを活用し、複雑な自動ルールを削ってからRLを入れる。

完了条件: 両作で初期中央値30秒以下、30エピソード後に中央値が1.5倍以上。

### Phase 3 — 新規の小型RLゲーム（3〜5週間）

1. One-Line RPG
2. Drone Bastion TD

One-Line RPGで、当たり判定を持つ1ライン格闘環境と高速headless学習を検証し、
その後、既存Escort TDの一部を流用して、重い機体物理と操作対象切替を持つ
Drone Bastion TDへ展開する。

完了条件:

- One-Line RPGで間合い管理、防御、連撃、必殺技温存のうち2つ以上が世代差として見える
- Drone Bastion TDで制動、砲台配置、危険方向への操作機切替が世代差として見える
- 両作とも初期中央値40秒以下、30エピソード後に中央値が1.5倍以上

### Phase 4 — 小さな制御問題（3〜5週間）

1. City Traffic
2. Network Ecosystem
3. Colony

完了条件: 行動の変化をログなしで画面から説明できる。

### Phase 5 — ネットワーク系の統合（3〜5週間）

- MOSS にルーティングRLを実装
- Submarine 2D/3Dのコア統合
- Network Small World を独立モードにするか判定

完了条件: 重複コードを増やさず、1つの学習コアを複数レンダラーから観察できる。

### Phase 6 — Planet Strategy（4〜6週間）

物流だけの環境から始め、固定敵、Championリーグの順で広げる。

完了条件: 報酬の抜け道を使わず、固定seed評価の勝率が世代とともに改善する。

## 8. 成功判定

### 8.1 全作共通の必須条件

- 起動後30秒以内に最初の意味ある判断が見える
- 初期モデルは2分以内に一度失敗する
- GAME OVER 後2秒以内に自動再開する
- 30分無操作でも停止・メモリ増大・UI待ちにならない
- 直近10回中央値とBestを常時確認できる
- 同一条件で Champion が旧モデルを上回る
- 新Tier直後は失敗が増え、その後回復する
- モデルを保存・復元しても評価結果が大きく崩れない

### 8.2 数値目標

ゲームごとに単位は違っても、次の比率で判定する。

- 30エピソード後の代表指標中央値: 初期10回比 `1.5倍以上`
- 100エピソード後: 初期10回比 `2倍以上` または次Tier到達
- Training の Champion 採用率: `10〜40%`
- 評価時の変動係数: 改善判定を壊さない範囲
- 60分連続実行時: フレーム時間とメモリが安定

平均値は極端に長い1回に引っ張られるため、主判定には中央値を使う。

## 9. 主なリスクと対策

| リスク | 症状 | 対策 |
|---|---|---|
| 報酬ハック | 動かず生存する、同じ行動を反復 | 進捗報酬、時間上限、行動コスト、リプレイ確認 |
| 恒久強化が学習を隠す | 数値だけで記録更新 | Skill固定評価、Power別表示 |
| 後半に学習が止まる | 長命だが世代が更新されない | step更新、短いheadless訓練、時間上限 |
| 状態爆発 | Q-tableが増え続ける | 観測削減、band化、上限と古い状態の整理 |
| 忘却 | 新Tierで過去課題が下手になる | 過去Tier評価、複数seed、Champion保護 |
| 画面が説明不能 | AIの上達がログでしか分からない | 危険方向、意図、探索を盤面に重ねる |
| CPU負荷 | 常駐するとPCが熱い | 訓練1本、負荷連動停止、描画FPSと訓練TPSの分離 |
| プロジェクト重複 | ネットワーク系が似たゲームになる | コア統合、表示モード化、独立価値の判定 |

## 10. 提案する意思決定

1. **Arena Shooter を完成品扱いせず、共通RL仕様のリファレンスにする**
2. **最初の実移植先を Network Defense にする**
3. **全作を同時改修せず、1作でカーブを測ってから横展開する**
4. **Skill評価が成立するまで恒久数値強化を入れない**
5. **Submarine 2D/3Dは1ゲームの表示違いへ統合する**
6. **Network Small Worldは独立価値が出なければMOSSへ統合する**
7. **Planet Strategyは最後に扱い、物流だけから学習させる**
8. **「平均プレイ時間」ではなく直近中央値と固定seed Champion評価で判断する**
9. **One-Line RPGを1ライン格闘RL環境兼、高速学習テストベッドとして新規作成する**
10. **Drone Bastion TDは最大6機、直接操作1機とし、切替・重機動・壁防衛を学習対象にする**

## 11. 最初の実装チケット案

1. Arena headless simを複数seed・複数世代の統計出力へ拡張
2. `shared/rl/rl_types.ts` と汎用 `tabular_q_agent.ts` を作成
3. Arena固有の観測priorを環境側へ移す
4. Champion / Trainingの固定seed対戦を追加
5. Learning HUDを共通コンポーネント化
6. Network Defenseの観測・行動・終了条件を文書と型で固定
7. Network Defenseの既存ルールAIを切替可能にし、RL環境を実装
8. 100エピソードの学習カーブを保存する検証スクリプトを追加
9. 初期中央値と30エピソード後中央値を比較する回帰条件を追加
10. 実測結果を基に報酬とTier閾値を一度だけ調整

この10件が完了した時点で、全作展開の技術リスクと実際の開発速度を再見積もる。
その後はゲームを増やすより、1作品ずつ「学習していることが見える」状態まで仕上げてから
次へ進む。
